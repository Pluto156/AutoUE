# 当前节点职责清单

## 口径

本文件只记录当前 `repo/AutoUE/config/workflows/puerts_ts.json` 里的节点事实。

当前 workflow 共有：

- 9 个 `enabled: true` active 节点。
- 5 个 `enabled: false` disabled / banned 节点。

- 当前 active 节点能生成实体/行为拆解、thin flow、UE API MCP 证据、PuerTS runtime mapping、TS ability/interactable 骨架和 eval instructions。

## 追问澄清：为什么 TypeScriptCodeGenerator 没有生成适配层

按设计目标，`TypeScriptCodeGenerator` 确实应该承接旧 `ModuleCodeGenerator` / `InteractiveObjectCodeGenerator` 的“实现代码生成”职责。

但当前代码实现还没有达到这个目标。当前 `TypeScriptCodeGenerator` 的真实行为是：

```text
PuerTSRuntimeMappingPlanner
+ TypeScriptScriptAnalyzer
+ TypeScriptInteractiveObjectGenerator
→ 为每个 analyzer target 选择 TypeScript 模板
→ 写 TypeScript/content/generated/*.ts
```

当前约束导致它没有生成 AIDev adapter：

1. `TypeScriptCodeGenerator` 只消费 `TypeScriptScriptAnalyzer` 给出的 `implementation_slots[].target_ts_file`。
2. validator 要求 `target_ts_file == PuerTSRuntimeMappingPlanner.runtime_owner`。
3. 本轮 `runtime_owner` 都是行为级 ability 文件，例如：
   - `TypeScript/content/generated/PlayerHorizontalMovementAbility.ts`
   - `TypeScript/content/generated/PlayerShortMeleeAttackAbility.ts`
   - `TypeScript/content/generated/EnemyHealthStateAbility.ts`
   - `TypeScript/content/generated/ExitRoomCompletionAbility.ts`
4. 当前模板只有：
   - `ability_module.ts.tmpl`
   - `interactive_object.ts.tmpl`
   - `runtime_bootstrap.ts.tmpl`
5. 当前 `runtime_bootstrap.ts.tmpl` 也只是写 `state/events` 的静态 bootstrap，不是 AIDev `CharacterAdapter` / `GameModeAdapter` / UE runtime actor。
6. schema 明确禁止 raw `files/content`，必须走模板渲染，因此 LLM 不能自由写一整套 adapter。

所以当前实际结果是：

```text
TypeScriptCodeGenerator 生成了行为级 TS 骨架，
但没有生成 UE/AIDev 可运行适配层。
```

这不是用户需求的最终形态，而是当前迁移实现的缺口。

## 原本 AutoUE 是怎么解决 UE 接入问题的

旧 AutoUE 默认链路不是靠 PuerTS adapter，而是靠 C++ / InteractiveObject / PCG 体系接入 UE。

旧链路大致是：

```text
ModuleAnalyzer
→ ModuleCodeGenerator
→ InteractiveObjectAnalyzer
→ InteractiveObjectCodeGenerator
→ PCGGraphComposer
→ PCGPlanner
→ EvaluateInstructionGenerator
```

旧接入方式：

| 旧节点 | 接入方式 |
|---|---|
| `ModuleCodeGenerator` | 生成 C++ module `.h/.cpp`，写入 UE 插件的 CustomModule 目录。 |
| `InteractiveObjectCodeGenerator` | 生成 C++ `A<Model>InteractiveObject` 类，继承 `AInteractiveObjectBase`，并重写/维护 `CustomModules.h`。 |
| `PCGGraphComposer` / `PCGPlanner` | 生成 PCG/场景摆放相关 JSON，例如 `ComposedGraph.json`，供 UE 侧工具链消费。 |
| UE 插件侧基类 | 通过 `IModuleBase`、`AInteractiveObjectBase`、`CustomModules.h` 等约定把生成代码挂进 UE。 |

也就是说，旧 AutoUE 解决接入问题的方法是：

```text
生成 C++ 类 + 依赖 UE 插件基类/注册文件 + PCG/场景 JSON
```

当前 PuerTS 迁移把这些 C++/PCG 节点禁用了，但还没有完全补上等价的 PuerTS/AIDev runtime adapter 生成能力。

## 2026-06-28 设计调整：砍掉过度新增节点，按 game-proto 最新口径收紧

用户确认：不采用上一版“新增一串 RuntimeAdapter / Combat / Camera / SceneHookup LLM 节点”的方案 B。原因是节点层级过多，会把问题从“生成能力不完整”变成“编排层更复杂”。

新的 Phase3 方向：**保留当前 9 个 active 节点主链，只改节点契约、输出 schema、模板与确定性 runner**。

### 对齐来源

参考 `D:\ClaudeTasks\active\game-proto-mapping\design\流程规范-8步.md` 以及相关 Phase 卡，采用以下口径：

```text
02 结构化拆解：分析时按 行为 → 能力 → 实体，机器产物仍以 entities[] → abilities[] → behaviors[] 落档
03 薄玩法流：Input → Ability/Action → SpatialQuery/HitQuery → Damage/Resource → Event/Result → Feedback/HUD → Cleanup
04 MCP 查询：只查 engine_port，不查行为名、能力名、实体名或公共系统名
05 Runtime 映射：必须显式 implementation_carrier / adapter_or_helper / verification_evidence
06 场景接入：必须区分 06C 声明 manifest 与 06D UE 实测 probe
08 验证：真实输入、runtime state、可见性、日志与截图都要回到 flow 证据
```

### 节点调整，不新增复杂层级

| 现有节点 | 调整后职责 | 明确不做 |
|---|---|---|
| `SceneAndGameplaySplitter` | 继续拆 `scene_description` / `gameplay_description`，但复杂系统要保留相机、VFX、UI、陷阱等体验要求，不可吞掉。 | 不做实体/能力/行为判断。 |
| `EntityAbilityBehaviorPlanner` | 改为“行为优先分析”：先从需求抽 `behaviors`，再归纳 `abilities`，最后挂到 `entities`；正式输出新增 `flow/02-structure.json` 和人读摘要。 | 不写 UE API、不写 runtime、不把 `camera/VFX/HUD/animation` 当大类桶。 |
| `ThinGameplayFlowPlanner` | 每个 behavior 必须 lower 到 thin flow；复杂交互必须覆盖 `Feedback/HUD` 与 `Cleanup`；如果有 `camera.*` / `vfx.*` / `animation.*` 实体，也必须有对应 flow。 | 不调用 MCP、不设计文件结构、不引入 `EntityRegistry/EventBus/TickGraph`。 |
| `UEApiMCPFeasibilitySearcher` | 只对 `engine_ports` 调 `ue-api-search.ue_api_semantic_search`；裁定统一为 `verdict=hit|miss`、`hit_type=direct_hit|indirect_hit`。 | 不用 `MCP status=ok` 冒充 hit；不查询行为/能力/实体名。 |
| `PuerTSRuntimeMappingPlanner` | 作为第 5 步主节点，补齐 `implementation_carrier`、`existing_framework_candidates`、`why_not_existing_framework`、`temporary_or_canonical`、`migration_path`、`adapter_or_helper`、`verification_evidence`。 | 不把所有行为都静默塞进 ability 文件；不把手写中间层冒充节点产物。 |
| `TypeScriptScriptAnalyzer` | 根据第 5 步 mapping 生成实现槽位，允许一个 behavior 关联 ability、runtime orchestrator、CharacterAdapter、GameModeAdapter、camera/helper 等多个模板槽位。 | 不再强制 `target_ts_file == runtime_owner` 成为唯一实现文件。 |
| `TypeScriptInteractiveObjectGenerator` | 继续生成交互对象/触发器侧 TS，但必须 trace 到 `behavior_id`、`flow_id`、`implementation_carrier`。 | 不创建 UE Actor 实例，不替代场景接入。 |
| `TypeScriptCodeGenerator` | 承担实现代码生成：在现有节点内扩模板，生成 ability、AIDev runtime orchestrator、CharacterAdapter、GameModeAdapter、camera/scene helper 等代码。 | 不新增单独 Combat/Camera/Adapter LLM 节点；不允许主 agent 手写 gameplay runtime。 |
| `EvaluateInstructionGenerator` | 输出验证计划时必须引用 02/03/04/05/06/08 证据链，包含相机可见性、复杂交互、runtime state 与截图口径。 | 不执行 PIE，不代替 deterministic validator 判定 done。 |

### Runner / validator 归属

UE Editor、PIE、按键输入、截图、runtime 采样、`06C/06D`、`08-runtime-summary`、`flow-gate.json` 由确定性 runner/validator 负责，不作为新增 LLM 节点。

目标是：

```text
LLM 节点负责判断/设计/模板参数
确定性代码负责写文件、清理、复制、编译、启动 UE、采样、判定 gate
```

### 下次从零重跑的复杂系统输入

下一次 clean baseline 后使用偏复杂但仍单房间可验收的输入，不再用极简一敌一出口样例：

```text
Create a compact side-scroller combat room. The player can move left and right, perform one short melee attack, and briefly dash. There is one patrolling melee enemy with health and defeated state. Add one ice trap in the room: when the player overlaps it, the player becomes frozen for a short time, movement is blocked, a freeze VFX appears, and the side camera gives a small feedback shake. The exit is locked until the enemy is defeated, then reaching the exit completes the room. Keep it one room and do not add inventory, quests, upgrades, ranged weapons, or complex UI.
```

该输入强制覆盖：

- 行为 → 能力 → 实体：`player`、`enemy.patrol_melee`、`hazard.ice_trap`、`exit.locked_room_exit`、`camera.side_follow_feedback`、`vfx.freeze_burst`。
- thin flow：移动、冲刺、近战、敌人巡逻/受击死亡、冰冻陷阱 overlap、冻结状态阻止移动、出口锁/解锁/完成、相机/VFX 反馈。
- MCP engine ports：输入绑定/移动、trace 或 overlap、damage、actor transform、timer、visibility/camera/view target、component visibility 或 Niagara/替代 VFX。
- Runtime mapping：不得把冰冻、相机、出口、战斗都塞进一个手写 runtime；必须由第 5 步声明 carrier 后由模板生成。
- 场景验证：`06C-manifest.json` 声明 actor，`06D-scene-probe-strict.json` 实测 PlayerStart/floor/camera/关键 actor 可见性。
