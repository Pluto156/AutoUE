## Phase1 定稿结论

Phase1 已完成原流程审计和迁移契约冻结。关键结论：

- `default.json` 仍是 11 节点 legacy C++/PCG/RAG 流程。
- `puerts_ts.json` 已在 Phase2 改为 9 个 active TS/PuerTS 节点；旧 C++/PCG/RAG 节点保持 disabled/banned。
- `ModuleCodeGenerator` 与 `InteractiveObjectCodeGenerator` 仍有真实 `.h/.cpp` 写文件逻辑，只能作为 legacy/default 残留，不能进入 PuerTS active path。
- `RetrieveModel`、`PCGGraphComposer`、`PCGPlanner` 本轮禁用，不迁移。
- `SceneFormalizer`、`KeyElementExtractor`、`ModuleAnalyzer`、`InteractiveObjectAnalyzer` 的可用语义分别合并/迁移到 `EntityAbilityBehaviorPlanner` 和 `TypeScriptScriptAnalyzer`。
- `EvaluateInstructionGenerator` 保留，但只能消费 TS/PuerTS 链路产物。

## 不再接受的完成口径

以下只能作为局部证据，不能单独标 Phase done：

- scripted smoke 跑通；
- 单次真实 LLM 跑通；
- 只生成 `.ts` 文件；
- 只新增 `puerts_ts.json` 旁路；
- 只在 workflow 里禁用 C++/PCG 节点；
- 只写 prompt 禁止 `.h/.cpp`；
- validator 只检查 JSON 形状；
- 没有旧节点职责迁移表。

## 目标 Python 闭环

```text
输入玩法需求
→ 场景/玩法拆分
→ 实体-能力-行为结构化
→ thin gameplay flow
→ UE API MCP raw/adjudication
→ PuerTS runtime mapping
→ TS/PuerTS 实现槽位分析
→ TS/PuerTS 交互对象模板生成
→ TS/PuerTS runtime/ability 模板生成
→ 可执行验证计划生成
→ 输出目录产物静态验证
→ Python runtime validation harness（静态子项）
→ staged 到真实 UE/PuerTS runtime
→ 真实运行一条流程
→ runtime-summary.json / runtime-log.jsonl
→ 多输入运行报告
```

这条链路必须满足：

- active workflow 中没有误启用旧 C++ 代码生成节点；
- 每个旧节点职责都有“迁移 / 合并 / 删除 / 禁用”的明确裁决；
- 每个 LLM 节点输出有 schema，且失败中断；
- 每个关键上游产物被下游真实消费；
- 最终 `.ts` / `instructions.json` 能追溯到实体、能力、行为；
- 输出目录无 `.h/.cpp`；
- 模型搜索、RAG、PCG 资产、`LLMHttpServer` 本轮保持禁用，除非另开 Phase。
